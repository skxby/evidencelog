# golden-set-run —— Golden Set 回归

## 何时用
用户说「跑 Golden Set」「回归跑一遍」「五个场景过一下」「改完重跑」。

## 五个固定场景（《V1 编码计划》第 18 节）
目录 `tests/datasets/`：

| 场景目录 | 期望结果 |
|---|---|
| `normal/` | 正常日志 → 期望 L0、**无**异常 Insight |
| `cpu_anomaly/` | 命中 CPU 异常 |
| `memory_growth/` | 命中内存持续增长 |
| `crash/` | 命中进程崩溃 |
| `malformed/` | 坏格式 → **明确失败**，而非产出一份假报告 |

> 数据来源优先用 `logs/` 下的真实日志构造/标注；**不许用凭空合成的假数据冒充**。

## 步骤
1. 确认 5 个场景目录都存在且非空；缺哪个就先说缺哪个，**不许静默跳过**。
2. 逐场景跑完整链路：`上传 → 脱敏 → 解析 → 分组 → 分析 → Insight`。
3. 每场景记录四件事：
   - 是否崩；
   - **关键 Insight 是否命中**（对照上表期望）；
   - **fact 类结论是否都有有效 evidence**（`evidence_ids ⊆ 本次有效 event_id`）；
   - 本次 Run 的成本（`cost_actual`）。
4. 与历史成本对比，明显异常要直接标出来。

## 输出格式
| 场景 | 是否崩 | 关键 Insight 命中 | evidence 合法 | 成本(元) | 结论 |
|---|---|---|---|---|---|
| normal | | 期望无异常 | | | ✅/❌ |

结尾给：5 场景通过数、成本合计、与上次对比、Top3 需修项。

## 失败处理
- **`malformed` 场景必须失败**：若它「成功产出了报告」，判 ❌ —— 这违反红线 4「失败不静默」。
- 某场景解析报错 → 保留报错原文与首个坏行，不跳过、不改期望值迁就实现。
- 命中率不达标 → 报告实际命中与期望的差集，**不许放宽断言或改 Golden 期望来「通过」**。
- 成本异常 → 给出本次 vs 历史的 token 与单价拆解，定位是缓存未命中还是档位被调高。
