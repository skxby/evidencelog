# stage-commit —— 阶段收尾与提交

## 何时用
用户说「提交阶段」「这个阶段做完了」「commit 一下」「收尾」。

## 前置：不许跳步
本技能只在**编码 + 单测都已完成**时使用。若测试还有失败，先修测试，不许用 `--no-verify`、不许删测试、不许放宽断言来「过」。

## 步骤

1. **跑测试并贴真实输出**（不许只说「通过了」）：
   ```bash
   pytest -q
   ```
   有失败 → 停下，先分析原因。**不许跳过或 mock 掉真实依赖。**

2. **对照本阶段「验收」逐条自评**：从《V1 编码计划》找到该阶段**验收**段落，逐条给「证据 + 实际结果 + 通过/未通过」。任一条无证据即视为未通过。
   > 想要独立复核（防自评放水），另用 `stage-verify` 技能。

3. **红线自查**（10 条硬约束逐条回答是/否 + 证据）：
   - 1 确定性计算有没有偷偷调 LLM？
   - 2 有没有把具体型号写进业务代码？（型号只能在 `.env`）
   - 3 有没有无 evidence 的 fact？越界 `event_id` 会被拦截吗？
   - 4 失败会不会静默？（该失败时必须明确失败）
   - 5 敏感原文有没有可能落盘？（脱敏必须在落盘前）
   - 6 有没有改动 9 表 / 7 态边界？（若改了，是否已获批）
   - 7 长任务是否都异步？（API 只返回 `run_id + queued`）
   - 8 Domain 是否走 Registry？核心 Runtime 有没有 import 具体 domain？
   - 9 是否只留最小接口缝、没有过度设计？
   - 10 是否已 commit 且消息带阶段号？

4. **提交**（消息格式固定，一个阶段一个 commit）：
   ```bash
   git add -A
   git commit -m "阶段 NN：<做了什么>"
   ```
   - 先确认 `.env` / `.venv` / `.uv-cache` / `.npm-cache` **没有被 `git add` 进去**（`git status` 看一眼）。
   - **不要 `git push`**，除非用户明确要求。

## 输出格式
| 项目 | 内容 |
|---|---|
| 改动文件清单 | … |
| `pytest -q` 实际输出 | … |
| 验收逐条结论 | 通过 N / 未通过 M（列出未通过项） |
| 红线自查 10 条 | 全 ✅ / 第 X 条 ❌ 及原因 |
| commit 哈希 + 消息 | … |
| 下一阶段建议 | … |

## 失败处理
- 任何验收项无证据 → 判**未达标**，不给「大概通过」，不提交。
- 红线自查有 ❌ → **不许提交**，先修；若该 ❌ 是「改了对象边界且未获批」，立即停下问用户。
- 发现工作区有未预期的脏文件（缓存、密钥、临时数据）→ 先补 `.gitignore`，再重新 `git status` 确认干净后提交。
